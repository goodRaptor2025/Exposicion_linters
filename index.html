ESLint: Reglas camelCase y naming-convention

Es la herramienta estandar para analisis de codigo en JavaScript y TypeScript. Se encarga de revisar que se sigan reglas de estilo y nomenclatura definidas por el equipo o la comunidad.

  • camelCase: Formato donde la primera letra es minuscula y cada palabra siguiente empieza con mayuscula (ej: miVariable, calcularTotal). La regla prohibe estilos como mi_variable.
  • naming-convention: Regla avanzada (especial en TS) que permite definir formatos distintos segun el tipo de elemento: variables, clases, tipos, parametros. Es mucho mas flexible y completa.

Pylint y flake8 para Python

Herramientas fundamentales para Python, basadas en la guia oficial de estilo PEP 8. Ambas revisan errores, calidad y convenciones de nombres.

Pylint

Muy completo. Exige estrictamente:
  • ✅ Funciones/Variables → snake_case
  • ✅ Clases → PascalCase
  • ✅ Constantes → MAYUSCULAS

flake8

Mas ligero, combina 3 herramientas:
  • 🔍 pyflakes: Encuentra errores logicos
  • 📝 pycodestyle: Revisa estilo PEP8
  • 📊 mccabe: Mide complejidad
3

Checkstyle para Java

Herramienta lider y estandar para revisar codigo Java. Se basa en las convenciones oficiales de Oracle, asegurando que todo el equipo escriba codigo identico en estructura y nombres.

Reglas principales de nomenclatura:

📦 Paquetes: todo.minusculas
🏛️ Clases / Interfaces: PascalCase
⚙️ Metodos / Variables: camelCase
💎 Constantes: UPPER_SNAKE_CASE
4

SonarQube: Analisis Estatico

Plataforma completa de calidad de codigo que funciona con casi cualquier lenguaje. No solo revisa nombres, sino seguridad, errores, duplicidad, mantenibilidad y mas.

✅ Detecta nombres incorrectos, confusos, muy cortos o largos.

✅ Genera informes, graficos y alertas centralizadas.

✅ Se integra con linters locales y pipelines de CI/CD.

Actua como el "inspector de calidad" de todo el proyecto.

5

Pre-commit Hooks: Validacion Automatica

Son scripts que se configuran en Git y se ejecutan antes de permitirte guardar o subir cambios al repositorio.

⚙️ Se programan para correr ESLint, Pylint, Checkstyle, etc., automaticamente.

✅ Si todo esta bien: Permite guardar el cambio.

❌ Si hay errores: Bloquea la accion hasta corregir.

Garantiza que ningun codigo incorrecto o que no cumpla reglas llegue al proyecto final.

Preguntas y Respuestas

1. ¿Como se configura ESLint para forzar camelCase?

Se instala y edita el archivo de configuracion .eslintrc.json:

{
  "rules": {
    "camelcase": ["error", {
      "properties": "always",
      "ignoreDestructuring": false
    }]
  }
}

Marca error si no se usa el formato correcto. En TypeScript se usa la regla mas avanzada @typescript-eslint/naming-convention.

2. Reglas de Pylint para convenciones

La regla principal es invalid-name, que valida contra PEP 8:

  • Funciones/variables → snake_case
  • Clases → PascalCase
  • Constantes → MAYUSCULAS

Otras reglas: too-short-name, too-long-name, mixed-case-variable-name. Se configuran en el archivo .pylintrc.

3. Integracion en GitHub Actions (CI/CD)

Se crea el archivo .github/workflows/lint.yml:

name: Revisar Codigo
on: [push, pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx eslint . # o pylint, flake8...

Si el linter encuentra errores, el proceso falla y bloquea la fusion del codigo.

4. ¿Renombrar automaticamente con linter?

Si, pero con condiciones:

  • ✅ ESLint: Si, con el comando npx eslint . --fix. Cambia mi_variable → miVariable automaticamente.
  • ❌ Pylint / flake8: No renombran, solo avisan. Se usan herramientas extra como autopep8 o rope.
  • ⚠️ Limitacion: Solo corrige el formato, no el significado ni nombres complejos o ambiguos.
